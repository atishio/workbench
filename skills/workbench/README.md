# Workbench

A portable development hub for agent harnesses. It knows the workspace
landscape — which repos exist, how to reach their services, what mock
infrastructure is available — and supplies default development practices for
developers, QA and reviewers, without modifying any workspace repo.

Works on any harness that can auto-invoke an instruction file and read files at
runtime. See [`SETUP.md`](SETUP.md).

## How it works

```
Package (this directory)          Instance (.workbench/)        Workspaces
────────────────────────          ──────────────────────        ──────────
SKILL.md          router          workbench.yaml   facts        agent config
SETUP.md          wiring          domain/          reference    conventions
framework/        defaults
SKILL-SCHEMA.yaml draft — non-normative, nothing reads it

Precedence: workspace always wins over hub.
```

The hub fills gaps. It never overrides a workspace's own approach.

## Getting started

### 1. Install

```bash
npx skills add https://github.com/atishio/workbench.git --skill workbench -a claude-code -y
```

[`SETUP.md`](SETUP.md) covers what the installer does not: wiring MCP servers for
the tool capabilities, recognising a harness that cannot run the package, and
confirming the install works.

### 2. Start working

On your first hands-on task the skill finds no `.workbench/` and runs init: a
seven-section interview that scans the project for evidence and has you decide
every value. Nothing it merely inferred gets written without your say-so.

### 3. That's it

No files are added to workspace repos. The hub reads their agent config as-is.

## What's in the box

### `SKILL.md`

The router. Deduces the mode (init, repair, migrate, or route), deduces the
role, identifies the workspace, applies precedence, and dispatches. Everything
else is read on demand, so ordinary tasks do not pay for the init script.

### `framework/protocol/`

Fallback protocols, used only where a workspace has no opinion of its own:

| Protocol | What it does |
|---|---|
| `init.md` | Build or repair the instance config, human-driven, section by section |
| `orient.md` | Identify workspace and role, check stack health, route |
| `dev-loop.md` | Change → verify → report, one change at a time |
| `probe.md` | Debugging has stalled — measure the system instead of guessing |
| `review.md` | Read a diff and report findings. Writes nothing |
| `ai-failure-modes.md` | The recurring ways this work goes wrong, and the guard for each |
| `grounding.md` | How every claim carries its source |
| `stub-and-capture.md` | Set up mocks, capture network flows |
| `test-scaffold.md` | Turn captured flows into test code |
| `verify/*.md` | Type-specific verification — `app-ui`, `app-be`, `test-suite`, and others |

`ai-failure-modes.md` and `probe.md` are the two worth reading before you need
them.

### `framework/ref/`

Tool references named by capability rather than by vendor — `ref-browser.md`
for driving a browser, `ref-tools.md` for what the workbench expects a harness
to provide and what to report when something is missing.

### `framework/templates/`

`workbench.yaml.example` is an annotated reference config for a fictional
project. `capture-context.md` is the handoff document between capture and test
scaffolding.

## The instance — `.workbench/`

Generated by init, specific to your project, and **committed**. It is
configuration reviewed in pull requests, not machine state — do not add it to
`.gitignore`.

```
.workbench/
  workbench.yaml     written by init; every value confirmed by a human
  domain/            hand-authored cross-repo reference material
```

## Roles

Declared during init, deduced at runtime from what you ask for.

- **Developer** — change code, verify each change, escalate to a probe when
  debugging stalls.
- **QA** — stand the stack up, drive the feature, capture real traffic, turn it
  into tests.
- **Reviewer** — read and report. Reviewer role **does not write to workspace
  source**; findings go in the report and the human decides which become work.

## Precedence

1. **Workspace authority** — its own agent config, always checked first
2. **Workspace conventions** — its style, test approach, lint rules
3. **Hub protocols** — fallback only
4. **Hub facts** — infrastructure from `workbench.yaml`, always available

If a workspace defines its own UI test skill, that skill is used — not
`stub-and-capture.md`. If a workspace has no agent config at all, the hub
protocols are the fallback.

## Extending it

| Goal | Do this |
|---|---|
| Add a hub protocol | Write `framework/protocol/{name}.md`; add a row to the routing tables in `SKILL.md` and `orient.md` |
| Add a verify type | Write `framework/protocol/verify/{type}.md` inheriting `common.md` |
| Add a mock adapter | Add it to the appendix in `stub-and-capture.md`; four operations is the whole contract |
| Change workspace behaviour | Do not touch the hub. Add a skill to that workspace — it takes precedence automatically |
| Update infrastructure facts | Let repair mode do it, so the provenance rules still apply |

**`SKILL.md` does not grow.** It is always loaded, so anything added to it
displaces something else. New material goes in `framework/` and gets a row in
the index.

## Grounding

Every output cites its source: `observed` from a running system, `confirmed`
by a human, or `inferred` — which must be flagged. A check that could not run
produces *unknown*, never *fine*. See `framework/protocol/grounding.md`.
